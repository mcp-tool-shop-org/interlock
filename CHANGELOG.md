# Changelog

## [Unreleased]

### Fixed

- **A per-cell wall cap.** `request_timeout_s` is clamped to 120 to 900 s per request, so a slow, fully resident c4 or c8 cell could take four passes of 900 s (an hour) plus up to six calibration calls, and a few such cells in a 3-quant window on an 80 or 96 GB card could pass Colab's roughly 4 h VM-loss line. A cell now has `CELL_WALL_S = 1800` (`settings.cell_wall_s` on every generate-ladder row). After calibration, a cell whose projected wall, `(1 warmup + repeats) x (ceil(3 x concurrency x t_verify_s) + 60)` from the real unclamped estimate, is over the cap is refused before any timed pass and recorded as `timeout` (`projected N s > cell wall 1800 s; not run`). `CELL_DEADLINE_S` (2 x the cap) is the outer bound over the whole cell: whatever call is blocked, the cell ends as an `unmeasured` row and the ladder carries on. The harness cannot see the window's wall; the launcher's wall stays the outer bound of the window.
- **`CALIBRATION_TIMEOUT_S` is 300 s (was 900).** A calibration call is a single request with a one-token reply. The slowest fully resident one on record is T4 r3's p16384 verify at 25.1 s (Ollama's Go side costs about 0.57 ms per prompt token on 2 vCPUs, so p32768 projects to about 70 s); the rig's 33k prefill takes 3.7 s. 300 s is more than four times the slowest projection, and a stuck cell's calibration is now bounded at 30 minutes instead of 90.
- **The T4 r4 hang: a VRAM sample has a deadline.** After the c4 16k cell's host-RAM `oom` row the run sent nothing for 56 minutes and its run record stayed `closed: false`; the likely place is the NVML sample at the start of the next cell, which has no timeout of its own and ran just after the kernel's OOM killer took a CUDA process (not proven; the r4 run printed no per-phase marker). Every VRAM sample now runs on a daemon thread with `SAMPLER_TIMEOUT_S = 30`; on expiry the cell is `unmeasured` (`VRAM sampler did not answer within 30 s`) and the ladder continues, so a wedged NVML costs 30 s a cell, not the window. A sampler that fails (rather than hangs) is still a `sampler_error`; the first sample of a cell used to propagate its exception raw and now follows the same rule.
- **After the first NVML timeout the run samples through `nvidia-smi`.** An NVML call abandoned on a daemon thread can leave pynvml wedged inside the process, so every later cell could wait out the 30 s deadline again for the rest of the run. The run's sampler (`GuardedSampler`, one per run) now switches, after its first timeout, to `nvidia-smi --query-gpu=memory.used,memory.total` run as a subprocess with a `NVIDIA_SMI_TIMEOUT_S = 10` timeout: a hung `nvidia-smi` is killed, so a wedged driver costs at most 10 s a sample and cannot pin the process. If `nvidia-smi` is missing, fails, answers nonsense or times out, the cell is `unmeasured` with the real reason and the ladder continues. Each generate row records `settings.vram_sampler` (`nvml`, `nvidia-smi`, or `nvidia-smi-fallback`) and `settings.vram_sampler_reason` (why the run switched).
- **Phase markers.** The harness writes one line per phase to stderr (`[interlock HH:MM:SSZ] cell p32768 c4: start, sampling VRAM`, each probe and verify sent, calibrated, each pass sent and answered, VRAM sampled, cell end), so the next hang names its own call.
- **No "margin of 0.0 MiB" clause.** When Ollama gave the system memory in MiB there is no GiB rounding margin, and the host-RAM reason no longer prints one.

### Added

- **A rig-check identity.** The Linux ladder only accepted Colab identities, so rig checks of the harness had to pass a placeholder `colab:L4` and their rows were labelled as L4 data. `RemoteDeviceIdentity.rig(card, vram_mib, driver_version, cuda_version)` is provider `rig` with a free-text card (`RTX 5090`), pool `rig-local`, and device `rig:RTX5090`. Every row built with it carries `not_for_import: true`. The routing-row schema allows the rig form only with `not_for_import: true` (a `rig:` row without it fails validation); Colab identities and rows are unchanged. `interlock import` refuses a rig row or a rig-provider envelope, naming `not_for_import`, and `route` excludes one that reaches a table with the new code `rig_check` (in the route-decision schema) and never ranks it.

## [1.0.7] - 2026-10-26

### Fixed

T4 rung r3 (the log of its Ollama and the VM's `free -m`) showed that version 3 labelled some cells wrongly. `GENERATE_LADDER_VERSION` is now 4. **The `timeout` and `unmeasured` labels that v3 gave to a partially offloaded cell or to a cell killed for host RAM are superseded by v4's `oom`** (the T4 r3 rows stay as data under their v3 labels). The router guard stays keyed on version 3 (`LADDER_MEASURED_FROM`): a v3 row's measured ttft and throughput are still valid.

- **A partial offload is `oom`, found before any timed call.** In r3 three cells (p32768 c1, p8192 c4, p4096 c8) loaded 27 to 29 of 33 layers on the GPU with 1.6 to 2.6 GB of KV in host RAM, then ran on the CPU until the 120 s request timeout, and were recorded as `timeout` because the calibration's verify call timed out before the residency check ran. The first calibration probe now loads the model at the cell's window and slots and the harness checks it is fully on the GPU: `/api/ps` `size_vram < size`, the load's `offloaded N/M layers` with N < M, or a `CPU KV buffer size` line. Any one of them raises `oom` with the evidence in the reason (`partial offload at num_ctx 34816 x 4 slots: 28/33 layers on the GPU, 2040 MiB of KV in host RAM, size_vram ... < size ...`; only what was read is named), before the second probe, the verify calls or any timed call, and the row records `settings.offload` (layers, host KV, sizes, and where each was read). The log is read by `LinuxOllamaServer.load_report()` / `parse_load_report` from the process's part of the server log (latest load; every value is `None` when absent), and an older server without the method still works.
- **A SIGKILL during a load is `oom` (host RAM) only on the log's numbers.** In r3 five cells logged 14 to 95 GB of host KV on a VM with 12,975 MiB of RAM and no swap, then `llama-server process has terminated: signal: killed`, recorded as `unmeasured`. When a call fails with `signal: killed`, the harness reads the same load report; if `CPU KV + CPU_Mapped weights` is greater than Ollama's `system memory` total it records `oom` (`host RAM: the load needed X MiB in host RAM (CPU KV K + mapped weights W); the VM has Y MiB (Ollama system memory)`). With no numbers, or numbers that fit, it stays `unmeasured` with Ollama's message: host RAM is never inferred without them.
- **The request timeout is scaled from the cell's own verify call and recorded.** Every call used a fixed 120 s timeout. Calibration calls now get `CALIBRATION_TIMEOUT_S = 900` (single requests). Timed calls get `clamp(ceil(3 x concurrency x t_verify_s) + 60, 120, 900)` (`REQUEST_TIMEOUT_FACTOR`, `REQUEST_TIMEOUT_DECODE_ALLOWANCE_S`, `REQUEST_TIMEOUT_FLOOR_S`, `REQUEST_TIMEOUT_CEILING_S`), where `t_verify_s` is the accepted verify call's `(total_duration - load_duration)`. On 2 vCPUs Ollama's Go side costs about 0.57 ms per prompt token at c8, so a fully resident c8 cell at a big card's 32k could pass 120 s and be wrongly marked unable. `settings.request_timeout_s` is on every generate-ladder row, measured or failed (`LinuxOllamaServer.post` takes a `timeout`), and a `timeout` row reads `did not finish within X s (scaled from a T s verify call at concurrency C)`.
- **Host RAM needs all three numbers and the rounding margin.** The `oom (host RAM)` reading requires the CPU KV, the CPU_Mapped weights and the system-memory total to have all been read (a missing one makes the cell `unmeasured`, and the reason never prints a value that was not read; it used to count missing mapped weights as 0). Ollama prints the total in GiB to one decimal, so the host buffers must exceed the total by 51.2 MiB (half of 0.1 GiB), and the reason states the margin.
- **A cell reads only its own load from the server log.** The log offset is snapshotted at the start of every cell (`LinuxOllamaServer.begin_cell`), not only when the server restarts, and a `system memory` line with no `load_tensors` block after it is a load that was killed before its block, so it has no layers or buffers (it used to inherit the previous load's block and could be called host RAM with another cell's numbers).
- **A missing `total_duration` or `eval_duration` is `unmeasured`.** v3 fell back to load + prefill + decode, which hides the queue wait and the overhead and would bring back the concurrency inflation. The verify call's `total_duration` is required too.
- **`route --max-ttft-ms` no longer refuses on rows that have no measured ttft.** The unversioned fill-card rows (`prefix_caching` unset) made `_ttft_refusal` answer `prefix_caching_unknown` even beside v3 generate rows (reproduced in r3). When at least one row has a measured ttft, the rows without one are dropped before the comparison, and `notes` says how many.

### Changed

- **A failure row records the window that was sent, as a measured row does.** `settings.num_ctx` is the `num_ctx` the request sent and `settings.cell_tokens` the nominal cell, on every failure path of the generate ladder (`oom` from a partial offload or host RAM, `timeout`, `unmeasured`, `load_refused`, `ctx_exceeded`); an `oom` row's `num_ctx` now equals the window its own reason names (it used to say the nominal 16384 beside a reason that said 16903 was sent). A failure before any request was sent (a pre-registered refusal, a failure outside the measurement) never had a window: it keeps the nominal size in `num_ctx`, and `settings.num_ctx_source` says `nominal: no request was sent` (it is `sent` otherwise).
- `_ttft_does_not_scale` names the prefill, not the ttft, in its parameter and message (it has read `prefill_ms` since v3).
- `tests/fake_ollama.py` now reports a partial offload (`/api/ps`, and the `offloaded N/M layers` and `CPU KV buffer size` log lines), simulates the SIGKILL when host buffers exceed the VM's RAM, raises `TimeoutError` past the timeout a call was sent with, and gives a slow fully resident cell. The parser tests read lines from T4 r3's own log (`tests/fixtures/ollama_logs/0.40.11/`).

### Docs

- The handbook's experiments page describes ladder version 4: partial offload and host-RAM `oom` found before any timed call, the scaled request timeout (`settings.request_timeout_s`), and the window every failure row records.

## [1.0.6] - 2026-10-26

### Fixed

T4 rung r2 showed three defects in the generate ladder (`GENERATE_LADDER_VERSION` 2 and 1). All three are in Ollama v0.40.11's source and in r2's llama-server log.

- **The prompt could overshoot its window, and 16k and 32k came back unmeasured.** The window was `target + num_predict + 64`, the calibration accepted a prompt within 2% of the target and landed about 1.2% high, so at 16k and 32k the prompt reached `num_ctx - 1` and Ollama truncated it to about half (`limit=8290 prompt=16577`). The window is now `target + 2% + num_predict + 64`, the largest prompt the tolerance accepts, so nothing the calibration accepts can reach the truncation line. A verify reading that shows truncation while the prompt is above its estimate is cut back and tried again, up to four verify calls. `settings.num_ctx` is what the request sent; `settings.cell_tokens` is the nominal cell.
- **Every ttft in the ladder was a prompt-cache hit, not a prefill.** Ollama sets `cache_prompt: true` on every completion with no per-request switch, llama-server reuses the longest common token prefix, and the ladder resent one identical prompt for the verify call, the warmup and every repeat, so each timed pass evaluated about one token (15 ms at 512 tokens and 33 ms at 8,287 on a T4). `prompt_eval_count` still reported the full length, so the row looked right. Every timed call now starts with a prefix of its own (the call number and a per-cell nonce, from the first character), the calibration includes the prefix, and the verify call has its own. Two guards turn a cached cell into `unmeasured`: a prefill faster than 250,000 tok/s (`PREFILL_TOK_S_CEILING`), and, within a concurrency, a longer cell whose ttft is under 60% of the proportional growth from the first measured cell (`TTFT_SCALING_FLOOR`). Rows record `prefix_caching: off`.
- **The concurrency cells ran through one slot, and their throughput read about the concurrency times too high.** `OLLAMA_NUM_PARALLEL` defaults to 1, so the c4 and c8 requests queued, and the aggregate was `sum(eval_count) / max(eval_duration)`, where each request's own `eval_duration` leaves out the queue wait. The harness's Ollama now runs exactly `concurrency` slots (it restarts to change the count, and the ladder loops concurrency outermost so each count is set once; exact, not a floor, because KV memory is `num_ctx` times the slots). The slot count is read from llama-server's `n_slots` in the server log and recorded with its source (`parallel_slots`, `parallel_slots_source`); a server that logged fewer slots than the concurrency makes the cell `unmeasured`. The aggregate decode rate is the generated tokens over the pass's decode window, taken from Ollama's own per-request durations and not the client's clock: from the earliest decode start (`total_duration - eval_duration`) to the latest end (`max total_duration`); at one request it is exactly `eval_count / eval_duration` (`throughput_method: ollama_durations_decode_window`), and `route` ranks on it. Between the request and the first token there is time that is neither prefill nor decode (the rig measured 0.11 s at 512 tokens, 1.36 s at 8k, 2.27 s at 16k, non-monotonic), so a client wall clock cannot give a clean decode rate. `ttft_ms` is now the time to the first token (`total_duration - eval_duration - load_duration`), which is what `--max-ttft-ms` floors on; `prefill_ms` is `prompt_eval_duration` on its own, and the cache check reads that one; `overhead_ms` records the rest per row. The tokens over the client's whole pass are `end_to_end_tok_s`, and the per-request rate is `per_request_decode_tok_s`. A high-context, high-concurrency cell can honestly fail to load or run out of memory on a small card; it is recorded as that failure.

### Changed

- Each readiness poll of the harness's Ollama has a 2 s timeout inside the `ready_timeout_s` budget (it was a 30 s `urlopen` inside a 30 s budget, so one hung request used it all).
- `GENERATE_LADDER_VERSION` is 3. The newest-version filter keeps version 1 and 2 rows out of version 3 decisions.
- **`route` never reads what earlier ladders could not measure.** A ttft from a row that did not come from a version 3 ladder is never used for `--max-ttft-ms` (the floor cannot pass), and the throughput of a row with a concurrency above 1 from before version 3 is never used (it cannot rank or pass a decode floor). `route` says so in `notes` ("N pre-v3 row(s) with concurrency > 1 not used", "ttft of N pre-v3 row(s) not used"). `table` shows `ttft: not measured` and `throughput: not measured` on those rows. A decode figure at concurrency 1 is unaffected.
- **Rig harnesses, audited.** No row in `table/routing.jsonl` carries a ttft in its slots or settings, and the rig's generate rows (E3 OpenVINO, E3-REF and E4 Ollama) record end-to-end latency, not a ttft; none has a concurrency above 1. Read, not run: `harness/runner.py` generate steps repeat one prompt across warmups and repeats, and `harness/fill.py` resends its prompt in the confirm call after the load call, so a ttft from them would be a cache hit as well; `harness/e4b.py` takes its figures from the adapter and was not traced further. A row cannot be told which harness made it, so the router reads no ttft from a row without a version 3 stamp, whatever its harness.
- `tests/fake_ollama.py`: a fake that caches by longest common prefix, queues unless it has the slots, truncates by `contextShiftPromptLimit`, and keeps virtual time. The tests for each fix fail against 1.0.5.

### Docs

- README and handbook carry a correction notice: the generate ladder's time to first token and concurrency-above-1 throughput in 1.0.5 and earlier were not valid measures, and interlock no longer uses them. The handbook describes ladder version 3.

## [1.0.5] - 2026-10-26

### Fixed

- **A looped generation and a request timeout were recorded as `load_refused`.** `classify_linux_error` sent every error it did not recognise to `load_refused` (and still did, until this change), so Ollama's "prediction aborted, token repeat limit reached" and a Go-style "HTTP 500 after 2m0s" became rows saying the card refused to load the model (T4 rung r1: 10 phi3.5 cells and 3 ctx-32768 cells). A looped generation is now `generation_aborted` and a request timeout is `timeout` (the existing kind; not a new `timed_out`). `load_refused` is left for real load and VRAM refusals.
- **The generate ladder's prompt made some models loop, and it timed a shorter prompt than it recorded.** Version 1 sent `"token "` repeated; phi3.5 repeated it until Ollama aborted, so those cells timed a loop, not decode. Version 2 sends varied, deterministic text that ends in an instruction (`ladder_prompt`). `num_ctx` is now prompt + `num_predict` + 64 (it was the prompt length, so Ollama truncated the prompt to about half: `prompt_eval_count` 1,026 for a "2048" cell), and the word count is calibrated per cell: two small prompts that cannot overflow the window give the tokens-per-word ratio and the instruction's tokens (real Ollama truncates an overflowing prompt to about `num_ctx / 2` and reports that, so a reading from an overflowing prompt is never scaled up), then the real prompt is verified against the target within 2%, and a reading well under what the ratio predicts is reported as truncation. The row records the evaluated length (`settings.prompt_tokens`, `prompt_token_method: ollama_prompt_eval_count`); a prompt that cannot be brought to the target, or a reply with no `prompt_eval_count`, is `unmeasured`, never a row with a length it did not time. Ollama's "the prompt is longer than the context length" refusal (context shift off) is `ctx_exceeded`. Version 2 has not run on Colab, so this is its definition.
- **`load_refused` is only for a recognised load or VRAM refusal** ("unable to load", "error loading model", "failed to load model", "insufficient memory", "too large for system memory"; checked against Ollama 0.40.9 and 0.40.11). The runner-crash message ("... may be due to resource limitations") and "failed to load manifest" are `unmeasured`. Any other unrecognised error is `unmeasured`. The `oom` match is a word (`"room"` and `"bloom"` no longer match).

### Added

- `generation_aborted`, a failure kind for a cell that was not measured. It sits beside `sampler_error`: it says nothing about what the card can load, so a spec cannot pre-register it, the receipt reads it as untimed and never as a speed or a capability, and the router lists it under `excluded` and never ranks it. It is in the routing-row and route-decision schemas.
- The table copy of every unmeasured row (`sampler_error`, `generation_aborted`, `unmeasured`) no longer says "this device can't do this setting".
- `unmeasured`, a second kind for a cell that was not measured, with the same rules as `generation_aborted` (schemas, receipt, router `excluded`). It is what an unrecognised error and an un-calibratable prompt become.
- `settings.ladder_version` on every generate-ladder row, success or failure (`GENERATE_LADDER_VERSION`, now 2). A row without the field is version 1 (a Colab generate row; the rig's own harness rows have no version). `interlock route` considers only the newest version present for a device and model, ranks only within the newest version across devices, and says so in `notes` ("N older-ladder row(s) not compared", "ranked on ladder version 2 only; version(s) 1 not compared"); a device that has only version 1 still routes when asked for with `--device`. `interlock table` groups ladder rows by device, model and version and shows `ladder vN`. Only ladder cells (rows with a `concurrency`) carry a version: a fill-card row has none and keeps routing beside v2 rows. The newest-version filter runs right after the task, model and device steps, before any floor (within a device and model, and across devices), so a v1 row cannot win or be listed because a v2 row failed a floor. `settings.num_ctx` on a ladder row is the nominal prompt length; the request sent prompt + `num_predict` + 64. `settings.prompt_tokens_target` is the requested length; a failure row that has only a request says `prompt_token_method: requested_not_verified`. The legacy envelope importer keeps `ladder_version`, `prompt_tokens_target` and `prompt_token_method`.

### Docs

- README and handbook describe the unmeasured kinds (`generation_aborted`, `unmeasured`), generate ladder version 2 and its calibrated prompt length, and ranking within the newest `ladder_version`.
- `test_a_floored_v1_row_on_another_device_is_not_a_runner_up_beside_a_v2_winner`: the L4 v1 row is at 90 tok/s, under the 100 floor, so it is actually floored.

## [1.0.2] - 2026-10-25

### Added

- `interlock import --remote-window <file>` takes the routing-row JSONL that `interlock run` writes on Linux (one row per line, or one row object) as well as the `{run_id, date, remote_device, records}` envelope. The rows keep their `provenance`, `settings` and `notes` as written. A row that is not a `colab:` device, or is `descriptive` or `aborted`, or has a missing or malformed `id` or `model`, or fails the schema, is refused with the file name and the row (`file[1]`); a line that is not JSON is refused with the file and line (`file:2`).
- With `--remote-window` and no `--offers`, the window rows are merged into the existing `table/routing.jsonl`: duplicates are refused (`duplicate row id ...`), the table is sorted by id and replaced atomically. `import_receipts` is not called, so no sibling repo is needed.
- `interlock import --allow-shrink`: lets a full rebuild drop the rows it owns but no longer produces. Every dropped id is printed and written to `table/import-dropped.txt` before the table is written.
- `interlock run --no-watchdog`: runs a 5090 step with no VRAM watchdog heartbeat. It is never implied by an unset variable. The choice is written into the receipt's `notes` (and the `watchdog` field of an E4b pilot document), and the empty-card check still runs.
- Three paths are now settings, each read from an environment variable, then from `[paths]` in `interlock.toml` in the working directory, and recorded as given: `INTERLOCK_SCRATCH_ROOT` / `scratch_root` (offrig's scratch project, default `interlock-scratch` under the system temp directory), `INTERLOCK_WEIGHTS_HOT` / `weights_hot` (the cache an `hf_cache: hot` arm reads, default `hot/` under `HF_HOME` or the user's Hugging Face cache) and `WATCHDOG_HEARTBEAT` / `heartbeat` (the heartbeat file, no default). A malformed `interlock.toml` is a structured error.
- A test (`tests/test_portable_defaults.py`) scans `src/` for drive-letter, `/home/` and `/Users/` paths and fails on any. Its allow-list is empty.

### Changed

- A full `interlock import` rebuild replaces only the rows its own sources produce (the pinned imports and the E1 rerun) and leaves every other row in `table/routing.jsonl` as it is (E2-E4, remote windows, any other harness row). A rebuild that no longer produces a row it owns is refused (exit 1, the first missing ids, the table untouched) unless `--allow-shrink` is passed.
- A table that holds a duplicate row id is refused, naming the ids, by both the rebuild and the `--remote-window` merge.
- A missing or unreadable file, a non-UTF-8 table, or a bad JSON file in `interlock import` is a message on stderr and exit 1, not a traceback.
- A full rebuild reads `candidates.json` and renders `gaps.md` before it writes anything, then replaces `import-dropped.txt`, `routing.jsonl` and `gaps.md` atomically; a missing or invalid `candidates.json` exits 1 with the table and `import-dropped.txt` byte-identical.
- The full `interlock import` rebuild reads its three source repositories from configuration: `--source rnd|npu|aspire=<path>` (repeatable) or `[import.sources]` in `<root>/interlock.toml`; the flag wins. There is no default path in `interlock.importers`. Each source's pinned commit is unchanged and `require_pin` still runs; a clone that lacks it is refused, naming the commit. Each source's name, pin and path (as given) are written at the end of `table/gaps.md`, not into any row.
- With a source missing, the rebuild exits 1 naming each missing source, its pinned commit, and the flag and key that set it. `--remote-window` alone (the merge) needs no source.
- The NPU pin's comment names the rnd tag `data/npu-buildout-275e511`.
- With `WATCHDOG_HEARTBEAT` (or `[paths] heartbeat`) unset, a run that uses the 5090 refuses before any device is touched, with a message that names `WATCHDOG_HEARTBEAT` and `--no-watchdog`. The same holds for the E4b block and pilot, and for an Ollama restart between steps. Before, an unset variable fell back to a heartbeat file at a fixed path on the author's rig.

Each search call on the row keeps its peak, shared usage, prompt rate and reason.
- The Ollama catalogue follows its recorded fixtures. `truncate_over_num_ctx` is a reply at `num_ctx` 8, which is what 0.35.1 returned. The no-limit cases note that `num_ctx` 64 did not bound them (11 prompt tokens and 144 eval tokens, stopped at end of turn); the 15 second timeout and the unload were the guard. The recorder accepts `--only`, `--num-ctx` and `--prompt-repeats` so one case can be recorded again.
- An OpenVINO embed, nli, or rerank step on the iGPU refuses a missing `static_shape` before compile, as the NPU already does. A dynamic iGPU shape is allowed only when the spec sets `dynamic_shape: true`, and that opt-in is recorded on the row. Generate is unchanged: it builds an LLMPipeline, not the graph that raises `rank().is_static()`. The fakes return the recorded output shape per task (position rows for embed, one flat label row for nli and rerank). Pooling `none` refuses a multi-row matrix instead of taking row 0. The real export drops its batch axis before pooling, and a vector with no batch axis is refused.
- A generate that is not the unload shape, including a companion stop, is a load. The recorder sends the unload and waits for the card before it checks that the card is idle again, including when that later check refuses. Each request is written to stderr as it is sent.
- After a recorded load, the recorder sends the unload and then polls the card and an empty `/api/ps` for about 10 seconds before it refuses. A refusal or error after a load still sends that unload, so the model is not left resident.
- The three no-limit recordings (`num_predict` 0, null, and missing) send `num_ctx` 64 and `shift` false, so the window ends the generate. The fixture keeps `behaviour` `no_reply`, so a fake still refuses, and it stores `eval_count` above 1. The recorder requires `--grant` and checks the heartbeat and an empty card before any request. The `num_predict` 1 fixture records `cold_load_s`. The count budget adds a prefill term: the longest count the spec can ask for, at 6,000 tokens per second.
- Ollama fakes check each request against a recorded exchange. `scripts/record_ollama_fixtures.py` writes those exchanges; it is run on the rig, and it refuses a cloud model or a card that is not idle. `num_predict` 0, null, and missing stay `no_reply` for the fakes. A token count stops after twice the cold-load allowance of the largest roster model (`/api/tags` size, or 16 GiB when the size is missing), plus that prefill term, and the arm is refused. `confirm_num_predict` below 1 is refused when the spec is validated, and again before a fill-card model is contacted.
- A hung local Ollama on `127.0.0.1:11434` is restarted between steps. Port `11490` is reported by `switchyard ollama-health` and is never stopped. Before the stop, the run re-checks the grant, the watchdog heartbeat, and that `/api/ps` lists no other session's model. `ollama serve` is replayed from the start line recorded for the run, and the log is appended. The CUDA library sha256, the server's `load_backend` line, flash attention, and the KV cache type must match. The first kept sample after a restart stays out of the warm percentiles. A slow request whose server still answers is left alone. At most two restarts a run. The step in flight is inconclusive, and a measurement taken across a restart is not kept.
- OpenVINO NLI and rerank steps take the model's flat logit row as their output. Pooling `none` used to expect one row per position, so a real cross-encoder failed with "'float' object is not iterable" (E4's sixth live run, iGPU, 2026-10-12). The fakes had returned per-position rows.
- The Ollama prompt fit estimates the seed repeats from the seed's own count, then trims only past the longest prefix known to be short. It used to add one seed per count, which took thousands of counts at a 118k-token target: E5's first live run spent over 30 minutes on one model without a row.
- The Ollama token count asks for one completion token, never zero. Ollama 0.35.1 reads `num_predict` 0 as no limit and generates until the context fills. E4's first live run (2026-10-11) sat at full card power for 12 minutes without writing a row. The zero-then-retry path is gone.

### Earlier development (before the first release)

Advisory only. `switchyard route` refuses when no measured row meets the constraints. It does not fall back, serve traffic, read a ledger, or call offrig. The bound is the conservative end of the measured spread, never a median. A parity miss is excluded. `thinking off` matches only off. `thinking on` matches any recorded thinking level, and the decision keeps that level.

#### Phase 0

Scaffold: the device allow-list, the grant and session guards, receipt validation, and CI with a coverage floor of 90. The iGPU is the Intel integrated GPU.

#### Phase 1

The routing table is built from pinned receipts.

#### Phase 2

The harness runs a committed spec and writes receipts. A rejected compile, a hang, and a lost device are recorded, and they are not speed.

#### Phase 3

E1, E2, and E3 measure embed and small-model generation on CPU, the Intel iGPU, and the NPU. A 5090 reference anchors Qwen3-8B.

#### Phase 4

`switchyard route` chooses from that table. The choice is one pure function of the rows and the request. When the set is empty, the command exits 1 and names the constraint. It does not guess.
