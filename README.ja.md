# インターロック：ローカルAIデバイスルーター

> **プロトタイプ、0.1.x：研究用ツール。** CLI、レシート形式、および実験仕様は、0.xリリースの間で予告なしに変更される場合があります。インターロックはあくまで推奨ツールです。モデル、エンジン、およびデバイスを提案するだけで、実際にトラフィックを処理することはありません。すべての数値は、1つの環境（Intel Core Ultra 9 285K、NPUおよびiGPU、およびRTX 5090）で測定されました。その結果を、一般的なベンチマークではなく、その環境の証拠として扱ってください。

鉄道のインターロックシステムは、列車が競合する経路に進入しないように制御します。このツールは、デバイスに対して同様の制御を行います。各ジョブをモデル、エンジン、およびデバイスに送信します。

タスク（埋め込み、再ランキング、NLI、検証、生成）と、重要な制約（品質、レイテンシー、コンテキスト、推論レベル）を指定します。インターロックは、モデル、エンジン、デバイス、および設定を提示し、各数値の根拠となるレシートを表示します。OpenVINOのAUTOおよびHETEROプラグインは、モデルを選択した後でデバイスを選択できます。この一連の流れの中でモデルを選択する機能はありません。このギャップが、このツールの提供する価値です。

## インストール

クローンからのインストール：

```
uv sync
uv run interlock --help
```

PyPIからのインストール（v0.1.0から）：

```
pip install mcptoolshop-interlock
```

```
uv tool install mcptoolshop-interlock
```

パッケージ名は`mcptoolshop-interlock`です。インポートとコマンドは`interlock`です。Python 3.12のみ（`requires-python`は`>=3.12,<3.13`）。CIはUbuntuでテストを実行します。ライブ測定の実行は、この表の数値が測定されたWindows環境に対して記述されています。

このプログラムがアクセスできる範囲は、[脅威モデル](#threat-model)に記載されています。

レシートスキーマ、ルーティングテーブル、およびハーネスが最初に作成されました。`interlock route`がそのテーブルを読み込みます。デバイス時間を消費することはありません。

## 現在のテーブルの内容

ルーティングテーブルには、コミットされたレシートから509行のデータが含まれています。すでに提供されている回答のいくつか：

- **小型モデルはIntel環境で良好に動作します。** Phi-3.5-miniは、CPUおよびiGPUで約20〜22トークン/秒、NPUで約15トークン/秒の速度で、1024トークンのプロンプト（推論なし）をデコードします。これにより、5090をより大きなタスクに利用できます。
- **8BモデルはIntel環境には適していません。** 同じ1024トークンのプロンプト（推論なし）で、Qwen3-8Bは、CPU、iGPU、およびNPUで約10〜12トークン/秒の速度でデコードされます。5090では、推論なしで約208トークン/秒、推論ありで211トークン/秒でデコードされます。5090がビジー状態の場合に15トークン/秒を要求すると、ルーターは拒否し、そのギャップの理由を説明します：`interlock route --task generate --model qwen3-8b --min-tok-s 15 --busy 5090`。
- **一部の形状では実行できません。** NPUは、512トークンの入力でQwen3-Embeddingを拒否しました。これは、一度に1つずつ、または8個のバッチで実行しようとした場合です。これらの行は、機能の確認として保持され、遅い候補としてランク付けされることはありません。

これらの数値は、E3およびe3-refレシートに記録されたデコードレートです。実行に関する注記は、[experiments/e3/run-notes-2026-10-10-11.md](experiments/e3/run-notes-2026-10-10-11.md)にあります。`interlock route`は、中央値ではなく、最悪の繰り返しに基づいてランク付けするため、その選択はこれらの概要よりも慎重です。

## 実行しないこと

インターロックはトラフィックを処理せず、リクエストをプロキシしません。モデルをトレーニングすることも、offrig、npu-serve、またはrndを編集することもありません。これらは、それぞれの所有者に委ねられます。サービングレイヤーには、独自の仕様が必要です。

## デバイス

すべてのデバイスには名前が付けられています。

| 名前 | デバイスの説明 |
|---|---|
| `NPU` | Core Ultra 9 285KのIntel AI Boost |
| `iGPU` | Intel GPU。ライブ列挙では、ベンダーが`0x8086`、デバイスタイプが`INTEGRATED`であることが確認される必要があります。完全な名前が記録され、決定は行われません。 |
| `CPU` | 同じプロセッサのCPU |
| `5090` | Ollamaを通じてのみアクセス可能なRTX 5090（アドレスは`127.0.0.1:11434`） |

`GPU.1`は、この環境でOpenVINOが認識する5090です。リゾルバーは、名前またはベンダーが変更された場合でも、このインデックスを拒否します。また、ベアの`GPU`、`AUTO`、`HETERO`、および`MULTI`も拒否し、ベンダーが`0x8086`および`INTEGRATED`でないGPUも拒否します。デバイスプロパティがどちらも含まれていないリストでも、完全な名前には「Intel」が含まれている必要があります。デバイスが存在しない場合はエラーになります。インターロックは、より弱いデバイスにフォールバックすることはありません。

NPUは排他的に使用されます。5090ステップは、Publisherの許可内でのみ実行されます。ランナーは、その許可を記録します。CPU負荷の高いステップは、Publisherが発表するウィンドウを待ちます。

## レシート

ルーティング行には、タスク、モデル（リポジトリまたはタグ、リビジョンまたはダイジェスト、量子化、ライセンス）、エンジンとそのバージョン、デバイス、設定、および測定された品質とレイテンシーが記載されています。品質メトリックは、それぞれ独自の`n`、間隔、およびデータセットハッシュを持ちます。レイテンシーは、コールドスタートとウォームスタートを区別します。単一の実行は、一時的なものとしてマークされます。行は、ソースレシートとインポート元のコミット、または実験仕様と実行IDを指します。

実行は、速度の代わりに、機能行を記録することもできます。`device_lost`と`hang`には、タイミングは含まれません。`native_binary_rejected`（デバイスがモデルをコンパイルし、実行時にネイティブバイナリを拒否した場合）は、コンパイル時間のみを証拠として保持し、モデル、デバイス、および静的な形状に限定されます。同じキーを持つもののみが実行されず、デバイスの他の形状は引き続き実行されます。これら3つすべては一時的なものであり、速度としてカウントされることはありません。スケジューリング中にアボートが実行されたステップは、レシートに`aborted: true`としてマークされ、実際に完了したスロットが記録されます。ルーティングテーブルは、アボートされた行を拒否し、`table/gaps.md`はアボートされた実行をリストします。監視スレッドは、メインスレッド外からすべての実行を保護します。ネイティブコンパイルが`compile_ceiling_s`（デフォルトは900秒）を超えて実行された場合、それは`compile_timeout`の機能行として記録され、システムRAMが88％に達すると実行がアボートされます。どちらの場合も、最初にレシートをフラッシュし、プロセスを終了コード75（コンパイルタイムアウト）または76（RAM停止）で終了します。すべての実行は、デバイスにアクセスする前に`receipts/<run_id>.run.json`も書き込みます（gitで無視され、レシートではありません）。そのため、外部から実行を強制終了しても、実行が開始されたという記録が残ります。外部から実行をクリーンに停止するには、`receipts/<run_id>.stop`を作成します。監視スレッドは、レシートをフラッシュし、コード77で終了します。

```
interlock check
```

これにより、`receipts/`と`table/routing.jsonl`の下にあるすべてのレシートが検証されます。空のツリーは問題ありません。レシート内のホームディレクトリパスは問題があります。

## 実行ライフサイクル

実行は、2つの状態のうちいずれかで終了します。完了した実行は、`receipts/<run-id>.jsonl`を残し、E4bの場合は、そのシリーズも残します。途中で停止した実行は、最初にそのレシートを書き込み、完了した呼び出しと`aborted: true`を記録し、次にレシート、シリーズ、ログ、および実行マーカーを`aborted/<run-id>-<sha>/`に、`NOTE.json`（実行ID、ハーネスSHA、開始と終了、例外、およびファイル）とともに移動します。`aborted/`はgitignoreされます。これは結果ではありません。`interlock import`はそれを読み取りません。また、これらの実行はルーティングテーブルに到達することはありません。

`receipts/`には、レシートのない`*-series/`ディレクトリを含めることはできません。次の実行は、そのようなディレクトリが存在する場合は開始を拒否し、`interlock runs quarantine <run-id>`という名前を付けます。

```
interlock runs list
interlock runs quarantine <run-id>
```

`list`は、各実行IDと状態（`complete`、`aborted`、または`stray`）を出力します。`quarantine`は、孤立したものをメモとともに`aborted/`に移動します。どちらのコマンドもOllamaまたはデバイスを開始しません。`--quarantine`は、隔離されたディレクトリを選択します。デフォルトは、実行ルートの下の`aborted/`です。

`--run-id`がない場合、E4bは`e4b-block`または`e4b-pilot`、次に`<base>-2`、`<base>-3`などを使用します。選択されたIDは、実行の最初の行と、レシートのフィールドになります。レシート、シリーズディレクトリ、ログ、コンパイルキャッシュ、または隔離された実行によってすでに使用されている名前は拒否されます。

## 脅威モデル

interlockは、ローカルデバイスとローカルHTTPに触れ、ネットワークを使用して、実験仕様ですでに名前が付けられているモデルを、そのモデルのパブリッシャーからダウンロードします。

- レシートとルーティングテーブルはローカルファイルです。
- 実行が実際に開始された場合、Ollamaの呼び出しは`127.0.0.1:11434`（5090）または`127.0.0.1:11490`（CPU）に送信されます。クラウドモデルタグは拒否されます。
- 実行が実際に開始された場合、OpenVINOの実行は`NPU`、`CPU`、またはIntel iGPU（ベンダー`0x8086`および`INTEGRATED`）を使用します。それらは決して`GPU.1`を選択しません。
- `--grant`なしの5090ステップは開始されません。NPUまたはiGPUステップで`--npu-session`がない場合、開始されません。
- 5090パスは、VRAMウォッチドッグのハートビートが最大60秒以内であり、モデルがロードされていないことを確認します。ハートビートファイルは開かれません。その修正時刻のみが読み取られます。
- ここでポートをリッスンするものは何もありません。
- interlockはテレメトリを送信しません。
- interlockはGPUをレンタルしたり、支出上限を設定したり、offrigのデータベースを開いたりしません。リモート価格は、日付付きのスナップショットファイルとしてのみ入力されます。

## レイアウト

`devices`は許可リストです。`guards`は許可、セッション、ハートビート、および空のカードです。`receipt`はスキーマと`interlock check`です。`importers`は、固定されたレシートから`table/routing.jsonl`を再構築します。`interlock table`は、そのテーブルをタスクまたはデバイスでフィルタリングして出力します。`table/gaps.md`は、実験のバックログです。ハーネスは、コミットされた仕様を実行します。`interlock route`は、そのテーブルを読み取り、デバイスには触れません。

ビルド概要と、それに含まれる4つのフィードバックノートは、`docs/handoff/`にスナップショットとして保存されます。スタジオメモリストア内のコピーは、常に信頼できるものとして保持されます。

## ルート

`interlock route`は、`table/routing.jsonl`から応答します。デバイスを開始したり、台帳を読み取ったり、offrigを呼び出したりすることはありません。

```
interlock route --task generate --model Phi --thinking off --ctx 1024 --busy 5090
```

`--model`は、リポジトリまたはタグのサブ文字列に一致します。ハイフンとコロンは無視されるため、`Qwen3-8B`は`qwen3:8b`に一致します。短いサブ文字列は、意図しないリポジトリに一致する可能性があります。一致したモデルが出力されます。`--thinking off`は、`off`にのみ一致します。`--thinking on`は、記録された思考レベルのいずれかに一致し、そのレベルを維持するため、OpenVINOの`low`アームは`low`のままです。`low`、`medium`、および`high`は、リクエストで指定された場合にのみ正確に一致します。`--min-tok-s`は、最小リピートスロットデコードレートの下限です。拒否は、その下限を`min_tok_s`という名前で示します。`--budget-left-usd`は、`--busy`のような入力です。最悪の場合がそれを超えるリモート行は、次点です。フラグがない場合、リモートの提案は、予算がチェックされていないとマークされます。`--as-of`は、デフォルトで今日の日付になります。ポリシー自体は、時計を読み取りません。

最も低いリピートスロットデコードtok/sでランクを生成します。他のすべてのタスクは、最も高いリピートスロットレイテンシ、またはリピートスロットがない行の最大クレームウォールでランク付けされます。マージンは、これらの保守的な境界間のギャップであり、中央値ではありません。タイの場合、5090は空きになります。30日より古い行は、古くなっています。プロビジョナルとマークされた行、またはリピートが2つ未満の行は、プロビジョナルです。どちらも引き続き対象となり、フラグが立てられます。

`native_binary_rejected`、`compile_rejected`、`compile_timeout`、`hang`、`device_lost`、および`parity_valid`がfalse（`parity_invalid`）の行は、それらのコードとともに、除外リストにリストされます。これらは候補ではありません。機能の成果は、行がパリティ無効である場合にも表示されるコードです。制約を満たす行がない場合、コマンドは1で終了し、セットを空にした制約の名前を表示します。フォールバックはありません。`--json`は、`src/interlock/schema/route-decision.v1.json`に対して有効なドキュメントを出力します。`--max-ttft-ms`は、比較されたすべての行が同じ`settings.prefix_caching`（`on`、`off`、または`default`）を記録している場合にのみ、拒否します。未設定は、不明であることを意味します。

リモートの提案には、`offrig_plan`オブジェクトが含まれます。interlockは、`offrig_plan`または`offrig_launch`を呼び出したり、支出を行ったりすることはありません。`docs/offrig-integration.md`を参照してください。

## 実験を実行する

すべての実験は事前に登録されています。その仕様は、質問、それが供給する決定、アーム、データセット、メトリック、および停止ルールとともに、デバイス時間が始まる前に、`experiments/<id>/spec.yaml`の下にコミットされます。`interlock run`は、コミット後に編集された仕様を拒否します。仕様のBLOBは、実行前（`require_unmodified`）にそのコミットに対してチェックされ、`--dry-run`によって出力されます。レシートには書き込まれません。E4bレシートは、ハーネス`git_sha`と`clean_tree`を記録します。フィルカードレシートは、`experiment_spec`と`run_id`を記録し、プレフライトが実行された場合は、`git_sha`と`clean_tree`も記録します。他の共有ランナーレシートは、`experiment_spec`と`run_id`のみを記録します。慣例として、ルールは結果が確認された後に変更されません。日付付きの修正は、結果がカウントされる実行の前に発生し、無効として設定された実行は、そのように記録されます。

```
interlock run experiments/e4/spec.yaml --dry-run
interlock run experiments/e4/spec.yaml --grant "<grant text>" --npu-session "<session>"
```

`--dry-run`は、計画と、実際の実行に必要なガードを出力し、何も開始しません。実際の実行には、デバイスが要求するフラグが必要です。5090の場合は`--grant`、NPUまたはiGPUの場合は`--npu-session`、CPU負荷の高いレッグの場合は`--cpu-window`です。1つのレシートを`receipts/`の下に書き込みます。次に、`interlock import`は、コミットされたレシートから`table/`を再構築し、`interlock check`はそれらを検証します。

## Ollamaがハングアップした場合

`interlock ollama-health`は、`127.0.0.1:11434`（5090サーバー）および`127.0.0.1:11490`（CPU専用サーバー）で`GET /api/version`を要求します。応答が5秒以内に到着した場合、ポートは正常です。コマンドは、各ポートに対して1行を出力し、どちらかがダウンしている場合は1で終了します。

実際の `interlock run` は、`127.0.0.1:11434` の間、ステップの間のみ、およびトランスポートエラー、実際のハングとなるタイムアウト、またはサーバーがダウンしている間の 5xx エラーが発生したステップの後にのみ、Ollama を再起動します。ダウンとは、2 秒間隔で 3 回の正常性チェックに失敗することを意味します。独自の期限に間に合ったリクエストは、正常性チェックが失敗した場合、または `/api/ps` がモデルの進行状況を示さない場合にのみ、ハングと見なされます。バージョンがまだ回答し、モデルがまだリストされている長いプロンプトは、ハングではありません。118k トークンのプロンプトは、処理が遅いという理由で終了されません。

ポート `11490` は、offrig の CPU インデクサーです。正常性チェックは引き続き正常と報告します。ダウンした `11490` は、実行を停止します。interlock は、そのプロセスを停止せず、再起動を許可する権限もありません。

何かが停止される直前に、再起動は `--grant`、ウォッチドッグのハートビート、および `/api/ps` を再確認します。別のセッションのモデルを指すリストは拒否されます。読み取れない `/api/ps` は、それ自体では、すでにダウンしているサーバーの再起動を妨げません。ハング中に、正常性チェックは引き続き正常と回答できます。読み取れない `/api/ps` は、別のセッションのモデルが確認される前に破棄されるため、再起動を拒否します。

停止されるプロセスは、`11434` でリッスンしているプロセスです。名前でプロセスを終了することはありません。トレイアプリは、それがリスナーでない限り、起動したままになります。`ollama serve` は、この実行のために記録された開始行から再生されます。argv、すべての `OLLAMA_*` および `LLAMA_ARG_*` 変数、およびログファイルです。stdout と stderr は、そのログに追加されます。interlock はサインインしません。`OLLAMA_CUDA_BACKEND` 変数はありません。バックエンドを強制する必要がある場合、変数は `OLLAMA_LLM_LIBRARY` であり、記録された開始行に含める必要があります。

レコードは、`INTERLOCK_OLLAMA_SERVE` という名前の JSON ファイルです。`SWITCHYARD_OLLAMA_SERVE`、`SWITCHYARD_OLLAMA_LOG`、および `SWITCHYARD_OLLAMA_EXE` は、このリリースでも機能し、警告を表示します。フィールドは、`argv`、`env`、`log_path`、`library_path`、`ggml_cuda_sha256`、および `backend_line` です。このリグで記録された 1 つの開始は、`cmd /c ollama serve` で、`OLLAMA_HOST=127.0.0.1:11434` および `OLLAMA_MODELS=E:/AI-Models/Ollama` を使用し、`E:/AI/ollama-cu134/system-11434.log` にログを記録します。ロードされたライブラリは `%LOCALAPPDATA%\Programs\Ollama\lib\ollama\cuda_v13\ggml-cuda.dll` です。そのファイルのパブリッシャーの sha256 は `6d3128e946bc9c95` で始まります。実行は、与えられた開始行を記録し、それを再生します。レコードが見つからない場合、何かが停止される前に再起動が拒否されます。

実行の開始時に、レコードの完全な `OLLAMA_*` および `LLAMA_ARG_*` セットは、ライブプロセスの環境と比較されます。その比較は正確です。プロセスの環境を読み取れない場合、サーバーの `server config` ログ行がフォールバックとなり、その比較も正確です。ログに記録されたデフォルトの一部のみを含むレコードは、再起動を無効にします。不一致は、この実行では再起動が行われないことを意味します。その理由は、実行マーカーに `ollama_restart_disabled` として記録されます。何も停止されません。`OLLAMA_HOST` は、`http://` または `https://` スキーマの有無にかかわらず一致します。

サーバーが復旧した後、実行はライブラリの sha256 を `library_path` から読み取ります。フラッシュアテンション、KV キャッシュのタイプ、`load_backend` 行、および完全な `OLLAMA_*` および `LLAMA_ARG_*` セットは、スプawn 後のログに書き込まれたバイトから読み取られます。それより前のバイトは、前のサーバーであり、その中の 1 つの行が一致しない場合、実行は停止します。ログのサイズを読み取れない場合、そのオフセットは不明であり、実行は停止します。ログが存在しない場合、ログは空であり、そのオフセットはゼロです。まだ書き込まれていない `load_backend` 行は、最初のモデルのロード後、およびそのサンプルが保持される前にチェックされます。行が見つからないか、異なる場合、実行は停止します。新しいセグメントのサーバー構成行は、実行が測定されたすべての変数をカバーする必要があります。プロセスが設定しなかったデフォルトもログに記録される場合があります。異なるライブラリまたは異なる環境で復旧したサーバーは、実行を停止します。`nvidia-smi` のドライバーの CUDA バージョンはチェックではありません。再起動では変更できません。ログにエコーされないフラッシュアテンションと KV キャッシュのタイプは、一致に失敗します。それらはレコードからコピーされず、読み取りとして扱われます。

サーバーが 60 秒以内に正常に動作しないか、カードがベースラインに戻らない場合、実行は停止し、Ollama を手動で開始するように指示されます。1 回の実行で再起動できるのは最大 2 回です。再起動が失敗した場合、その制限にカウントされます。

各再起動は、実行マーカーと `settings.ollama_restarts` に記録されます。いつ、どのポート、理由 (`down` または `hung`)、古い PID と新しい PID、正常になるまでの時間、およびバージョンです。実行中にあったステップは決定的なものではなく、成功とは見なされません。spec で `retry` が設定されている場合 (デフォルトはなし) のみ、再度試行されます。保持された再試行は、`settings.retried` を設定します。再起動後の最初の保持されたサンプルは、`settings.cold_after_restart` を設定し、ウォームパーセンタイルから除外されます。再起動をまたいでの測定は保持されません。

`--dry-run` は、このポリシーを出力し、どちらのポートにも接続しません。

## 開発

Python 3.12。`uv sync --frozen` は、ロックファイルからプロジェクト環境を作成します。NPU 環境は共有しません。OpenVINO 2026.4.1 が `intel` の追加の依存関係です。テストには必要ありません。

```
uv sync --frozen
uv run interlock check
uv run pytest
```
