# interlock：ローカルAIデバイスルーター

> **プロトタイプ、バージョン0.1.x：研究用ツールであり、リリース版ではない。** CLI、出力形式、および実験仕様は予告なく変更される可能性があり、現時点ではPyPIには何も公開されていない。interlockはあくまで推奨ツールであり、モデル、エンジン、およびデバイスを提案するだけで、実際にトラフィックを処理することはない。すべての数値は、単一の環境（Intel Core Ultra 9 285K、NPUおよびiGPU搭載、さらにRTX 5090）で測定されたものである。その結果を、一般的なベンチマークとしてではなく、あくまでその環境における証拠として扱うこと。

鉄道の連動装置は、列車が競合する経路に進入しないように制御する。このツールは、デバイスに対して同様の機能を提供する。各ジョブをモデル、エンジン、およびデバイスに送信する。

タスク（埋め込み、再ランキング、NLI、検証、生成）と、重要となる制約（品質、レイテンシ、コンテキスト、推論レベル）を指定する。それに対し、モデル、エンジン、デバイス、および設定が提示され、各数値の根拠となる情報も表示される。OpenVINOのAUTOおよびHETEROプラグインは、モデルが選択された後にデバイスを選択できる。この一連の流れの中で、モデルを選択する機能は存在しない。このギャップが、このツールの提供する価値である。

## インストール

まだ公開されていない。最初のリリースまで、クローンからインストールする。

```
uv sync
uv run interlock --help
```

最初のリリース後：

```
pip install mcptoolshop-interlock
```

```
uv tool install mcptoolshop-interlock
```

配布名：`mcptoolshop-interlock`。インポートとコマンド：`interlock`。Python 3.12のみ（`requires-python`は`>=3.12,<3.13`）。CIはUbuntuでテストを実行する。この表で測定に使用されたWindows環境で、ライブ測定を実行するスクリプトが用意されている。

このプログラムがアクセスできる範囲は、[脅威モデル](#threat-model)に記載されている。

ルーティングスキーマ、ルーティングテーブル、およびハーネスが最初に作成された。`interlock route`は、そのテーブルを読み込む。デバイス時間を消費することはない。

## 現在のテーブルの内容

ルーティングテーブルには、コミットされた結果から502行のデータが含まれている。すでに提供されている回答の例をいくつか示す。

- **小型モデルはIntel環境で良好に動作する。** Phi-3.5-miniは、CPUおよびiGPU上で約20〜22トークン/秒、NPU上で約15トークン/秒の速度でデコードを実行する（1024トークンのプロンプト、推論なし）。これにより、5090をより大きなタスクに利用できるようになる。
- **8BモデルはIntel環境には適さない。** 同じ1024トークンのプロンプト、推論なしの場合、Qwen3-8BはCPU、iGPU、およびNPU上で約10〜12トークン/秒でデコードを実行する。5090では、推論なしで約208トークン/秒、推論ありで211トークン/秒でデコードを実行する。5090をビジー状態にして15トークン/秒を要求すると、ルーターは拒否し、そのギャップの理由を説明する：`interlock route --task generate --model qwen3-8b --min-tok-s 15 --busy 5090`。
- **一部の形状では実行できない。** NPUは、512トークンの入力でQwen3-Embeddingを拒否した（一度に1つ、または8個のバッチ）。これらの行は、機能の確認として保持され、遅い候補としてランク付けされることはない。

これらの数値は、E3およびe3-refレシートに記録されたデコードレートである。実行に関する注記は、[experiments/e3/run-notes-2026-10-10-11.md](experiments/e3/run-notes-2026-10-10-11.md)に記載されている。`interlock route`は、中央値ではなく、最悪の繰り返し回数に基づいてランク付けするため、その選択はこれらの概要よりも慎重である。

## 実行しないこと

interlockはトラフィックを処理せず、リクエストをプロキシも行わない。モデルをトレーニングすることもない。offrig、npu-serve、またはrndを編集することもない。これらはそれぞれの所有者に委ねられる。サービングレイヤーには、独自の仕様が必要である。

## デバイス

すべてのデバイスには名前が付けられている。

| 名前 | 内容 |
|---|---|
| `NPU` | Core Ultra 9 285KのIntel AI Boost |
| `iGPU` | Intel GPU。ライブ列挙では、ベンダーが`0x8086`、デバイスタイプが`INTEGRATED`であることが示される必要がある。完全な名前が記録され、決定には使用されない。 |
| `CPU` | 同じプロセッサのCPU |
| `5090` | Ollamaを通じてのみアクセス可能なRTX 5090（アドレス：`127.0.0.1:11434`） |

`GPU.1`は、この環境でOpenVINOが認識する5090である。リゾルバーは、名前またはベンダーが変更された場合でも、このインデックスを拒否する。また、ベアの`GPU`、`AUTO`、`HETERO`、および`MULTI`も拒否し、ベンダーが`0x8086`および`INTEGRATED`でないGPUも拒否する。デバイスプロパティがどちらも含まれていないリストでも、完全な名前には「Intel」が含まれている必要がある。デバイスが存在しない場合はエラーとなる。interlockは、より弱いデバイスにフォールバックすることはない。

NPUは排他的に使用する。5090ステップは、Publisherの許可内でのみ実行される。ランナーは、その許可を記録する。CPU負荷の高いステップは、Publisherが発表するウィンドウを待つ。

## レシート

ルーティング行には、タスク、モデル（リポジトリまたはタグ、リビジョンまたはダイジェスト、量子化、ライセンス）、エンジンとそのバージョン、デバイス、設定、および測定された品質とレイテンシが記録される。品質メトリックは、それぞれ独自の`n`、間隔、およびデータセットハッシュを持つ。レイテンシは、コールドスタートとウォームスタートを区別する。単一の実行は、仮の状態としてマークされる。行は、ソースレシートとインポート元のコミット、または実験仕様と実行IDを指す。

実行は、速度の代わりに、機能行を記録することもできる。`device_lost`と`hang`には、タイミングは含まれない。`native_binary_rejected`（デバイスがモデルをコンパイルし、実行時にネイティブバイナリを拒否した場合）には、コンパイル時間のみが証拠として記録され、モデル、デバイス、および静的な形状に限定される。同じキーを持つもののみが実行されなかったとマークされ、デバイスの他の形状は引き続き実行される。これら3つすべては仮の状態であり、速度としてカウントされることはない。スケジューリング中に中断されたステップは、レシートに`aborted: true`としてマークされ、実際に完了したスロットが記録される。ルーティングテーブルは、中断された行を拒否し、`table/gaps.md`には中断された実行がリストされる。監視スレッドは、メインスレッド外からすべての実行を監視する。ネイティブコンパイルが`compile_ceiling_s`（デフォルトは900秒）を超えて実行された場合、それは`compile_timeout`の機能行として記録され、システムRAMが88％に達すると実行が中止される。どちらの場合も、最初にレシートをフラッシュし、プロセスを終了コード75（コンパイルタイムアウト）または76（RAM停止）で終了する。すべての実行は、デバイスにアクセスする前に`receipts/<run_id>.run.json`を書き込む（gitで無視され、レシートではないため）、外部から実行が停止された場合でも、実行が開始されたという記録が残る。外部から実行をクリーンに停止するには、`receipts/<run_id>.stop`を作成する。監視スレッドは、レシートをフラッシュし、コード77で終了する。

```
interlock check
```

そのリクエストは、`receipts/`と`table/routing.jsonl`の下にあるすべてのレシートを検証します。空のツリーでも問題ありません。レシートにホームディレクトリのパスが含まれていると、エラーになります。

## ライフサイクルを実行

実行は、2つの状態のうちいずれかの状態で終了します。完了した実行は、`receipts/<run-id>.jsonl`と、E4bの場合は、そのシリーズをその隣に記録します。途中で停止した実行は、最初にそのレシートを、完了した呼び出しと`aborted: true`とともに記録し、次にレシート、シリーズ、ログ、および実行マーカーを`aborted/<run-id>-<sha>/`に、`NOTE.json`（実行ID、ハーネスSHA、開始と終了、例外、およびファイル）とともに移動します。`aborted/`はgitignoreされます。これは結果ではありません。`interlock import`はそれを読み取りません。また、これらの実行はルーティングテーブルに到達することはありません。

`receipts/`には、レシートが存在しない`*-series/`ディレクトリを含めることはできません。次の実行は、そのようなディレクトリが存在する場合は開始を拒否し、そのディレクトリに`interlock runs quarantine <run-id>`という名前を付けます。

```
interlock runs list
interlock runs quarantine <run-id>
```

`list`は、各実行IDと状態（`complete`、`aborted`、または`stray`）を出力します。`quarantine`は、孤立したものをメモとともに`aborted/`に移動します。どちらのコマンドもOllamaまたはデバイスを開始しません。`--quarantine`は、隔離されたディレクトリを選択します。デフォルトは、実行ルートの下の`aborted/`です。

`--run-id`がない場合、E4bは`e4b-block`または`e4b-pilot`、次に`<base>-2`、`<base>-3`などを利用します。選択されたIDは、実行の最初の行とレシートのフィールドになります。レシート、シリーズディレクトリ、ログ、コンパイルキャッシュ、または隔離された実行ですでに使用されている名前は拒否されます。

## 脅威モデル

interlockは、ローカルデバイスとローカルHTTPにアクセスし、ネットワークを使用して、実験仕様ですでに名前が付けられているモデルを、そのモデルの公開元からダウンロードします。

- レシートとルーティングテーブルはローカルファイルです。
- 実行が実際に開始された場合、Ollamaの呼び出しは`127.0.0.1:11434`（5090）または`127.0.0.1:11490`（CPU）に送信されます。クラウドモデルタグは拒否されます。
- 実行が実際に開始された場合、OpenVINOの実行は`NPU`、`CPU`、またはIntel iGPU（ベンダー`0x8086`および`INTEGRATED`）を使用します。それらは決して`GPU.1`を選択しません。
- `--grant`なしの5090ステップは開始されません。NPUまたはiGPUステップで`--npu-session`がない場合も開始されません。
- 5090パスは、VRAMウォッチドッグのハートビートが最大60秒前のものであり、モデルがロードされていないことを確認します。ハートビートファイルは開かれません。その変更時刻のみが読み取られます。
- ここでポートをリッスンするものは何もありません。
- interlockはテレメトリを送信しません。
- interlockはGPUをレンタルしたり、支出上限を設定したり、offrigのデータベースを開いたりしません。リモート価格は、日付付きのスナップショットファイルとしてのみ入力されます。

## レイアウト

`devices`は許可リストです。`guards`は、許可、セッション、ハートビート、および空のカードです。`receipt`はスキーマと`interlock check`です。`importers`は、固定されたレシートから`table/routing.jsonl`を再構築します。`interlock table`は、そのテーブルをタスクまたはデバイスでフィルタリングして出力します。`table/gaps.md`は、実験のバックログです。ハーネスは、コミットされた仕様を実行します。`interlock route`は、そのテーブルを読み取り、デバイスにはアクセスしません。

ビルドの概要と、それに含まれる4つのフィードバックノートは、`docs/handoff/`にスナップショットとして保存されます。スタジオのメモリストアにあるコピーは、常に信頼できるものとして扱われます。

## ルーティング

`interlock route`は、`table/routing.jsonl`から応答します。デバイスを開始したり、台帳を読み取ったり、offrigを呼び出したりすることはありません。

```
interlock route --task generate --model Phi --thinking off --ctx 1024 --busy 5090
```

`--model`は、リポジトリまたはタグのサブ文字列に一致します。ハイフンとコロンは無視されるため、`Qwen3-8B`は`qwen3:8b`に一致します。短いサブ文字列は、意図しないリポジトリに一致する可能性があります。一致したモデルが出力されます。`--thinking off`は、`off`にのみ一致します。`--thinking on`は、記録された思考レベルのいずれかに一致し、そのレベルが保持されるため、OpenVINOの`low`アームは`low`のままになります。`low`、`medium`、および`high`は、リクエストでそれらが指定された場合にのみ正確に一致します。`--min-tok-s`は、最小リピートスロットデコードレートの下限です。拒否は、その下限を`min_tok_s`という名前で示します。`--budget-left-usd`は、`--busy`のような入力です。最悪の場合がそれを超えるリモート行は、次点となります。フラグがない場合、リモートの提案は、予算がチェックされていないとマークされます。`--as-of`は、デフォルトで今日の日付になります。ポリシー自体は、時計を読み取りません。

最も低いリピートスロットデコードtok/sでランクを生成します。他のすべてのタスクは、最も高いリピートスロットレイテンシ、または行にリピートスロットがない場合は、最大のクレームウォールでランク付けされます。マージンは、これらの保守的な境界間のギャップであり、中央値ではありません。タイの場合、5090は空きになります。30日より古い行は古いと見なされます。暫定とマークされている行、またはリピートが2つ未満の行は、暫定と見なされます。どちらも引き続き対象となり、フラグが立てられます。

`native_binary_rejected`、`compile_rejected`、`compile_timeout`、`hang`、`device_lost`、および`parity_valid`がfalse（`parity_invalid`）の行は、それらのコードとともに、除外リストにリストされます。これらは候補ではありません。機能の成果は、行がパリティ無効である場合にも表示されるコードです。どの行も制約を満たさない場合、コマンドは1を終了し、セットを空にした制約の名前を表示します。フォールバックはありません。`--json`は、`src/interlock/schema/route-decision.v1.json`に対して有効なドキュメントを出力します。`--max-ttft-ms`は、比較されたすべての行が同じ`settings.prefix_caching`（`on`、`off`、または`default`）を記録している場合にのみ許可されます。未設定は不明を意味します。

リモートの提案には、`offrig_plan`オブジェクトが含まれます。interlockは、`offrig_plan`または`offrig_launch`を呼び出したり、支出を行ったりすることはありません。`docs/offrig-integration.md`を参照してください。

## 実験を実行

すべての実験は事前に登録されています。その仕様は、質問、それが供給する決定、アーム、データセット、メトリック、および停止ルールとともに、デバイス時間が始まる前に`experiments/<id>/spec.yaml`にコミットされます。`interlock run`は、コミット後に編集された仕様を拒否します。仕様のBLOBは、実行前（`require_unmodified`）にそのコミットに対してチェックされ、`--dry-run`によって出力されます。レシートには書き込まれません。E4bのレシートは、ハーネス`git_sha`と`clean_tree`を記録します。フィルカードのレシートは、`experiment_spec`と`run_id`を記録し、プリフライトが実行された場合は、`git_sha`と`clean_tree`も記録します。他の共有ランナーのレシートは、`experiment_spec`と`run_id`のみを記録します。慣例として、ルールは結果が確認された後に変更されません。日付付きの修正は、結果がカウントされる実行の前に行われ、無効として設定された実行は、そのように記録されます。

```
interlock run experiments/e4/spec.yaml --dry-run
interlock run experiments/e4/spec.yaml --grant "<grant text>" --npu-session "<session>"
```

`--dry-run`は、計画と、実際の実行に必要なガードを出力し、何も開始しません。実際の実行には、デバイスが要求するフラグが必要です。5090の場合は`--grant`、NPUまたはiGPUの場合は`--npu-session`、CPU負荷の高いレッグの場合は`--cpu-window`です。1つのレシートを`receipts/`に書き込みます。次に、`interlock import`は、コミットされたレシートから`table/`を再構築し、`interlock check`はそれらを検証します。

## Ollamaがハングアップした場合

`interlock ollama-health` は `GET /api/version` (5090 サーバー) と `127.0.0.1:11490` (CPU 専用サーバー) に対して `127.0.0.1:11434` を問い合わせます。ポートが正常な状態であると判断されるのは、その応答が 5 秒以内に返ってきた場合です。このコマンドは、各ポートに対して 1 行ずつ出力し、いずれかのポートがダウンしている場合は 1 を返して終了します。

実際の `interlock run` は、輸送エラー、実際にはハングアップしているタイムアウト、またはそのサーバーがダウンしている間に発生した 5xx エラーが発生したステップの後にのみ、`127.0.0.1:11434` に対して Ollama を再起動し、ステップの間のみ再起動します。ダウンとは、2 秒間隔で 3 回の正常性チェックに失敗することを意味します。自身の期限内にリクエストが完了した場合、そのリクエストは正常性チェックに失敗した場合、または `/api/ps` がモデルの進行状況を示さない場合にのみ、ハングアップと見なされます。バージョンがまだ有効で、モデルがまだリストに表示されている長いプロンプトは、ハングアップとは見なされません。118k トークンのプロンプトは、処理が遅いという理由で強制終了されません。

ポート `11490` は、offrig の CPU インデクサーです。正常性チェックは、引き続き正常と報告します。ダウンしている `11490` は、実行を停止させます。interlock は、そのプロセスを停止させず、再起動を許可する権限もありません。

何らかの処理を停止する直前に、再起動は `--grant`、ウォッチドッグのハートビート、および `/api/ps` を再確認します。別のセッションからのモデルを指すリストは拒否されます。読み取り不可能な `/api/ps` は、それ自体では、すでにダウンしているサーバーの再起動をブロックすることはありません。ハングアップ中に、正常性チェックは引き続き応答できます。読み取り不可能な `/api/ps` は、別のセッションのモデルが確認される前に破棄されるため、再起動を拒否します。

停止されるプロセスは、`11434` でリッスンしているプロセスです。名前によってプロセスが強制終了されることはありません。トレイ アプリは、それがリッスン プロセスでない限り、起動したままになります。`ollama serve` は、この実行のために記録された開始行から再生されます。具体的には、argv、すべての `OLLAMA_*` および `LLAMA_ARG_*` 変数、およびログファイルです。stdout と stderr は、そのログに追加されます。interlock はサインインしません。`OLLAMA_CUDA_BACKEND` 変数は存在しません。バックエンドを強制する必要がある場合、その変数は `OLLAMA_LLM_LIBRARY` であり、記録された開始行に含める必要があります。

記録は、`INTERLOCK_OLLAMA_SERVE` という名前の JSON ファイルです。このリリースでは、`SWITCHYARD_OLLAMA_SERVE`、`SWITCHYARD_OLLAMA_LOG`、および `SWITCHYARD_OLLAMA_EXE` は引き続き機能し、警告を表示します。フィールドは、`argv`、`env`、`log_path`、`library_path`、`ggml_cuda_sha256`、および `backend_line` です。このリグで記録された 1 つの開始は、`cmd /c ollama serve` で、`OLLAMA_HOST=127.0.0.1:11434` と `OLLAMA_MODELS=E:/AI-Models/Ollama` を使用し、`E:/AI/ollama-cu134/system-11434.log` にログを記録します。ロードされたライブラリは `%LOCALAPPDATA%\Programs\Ollama\lib\ollama\cuda_v13\ggml-cuda.dll` です。そのファイルのパブリッシャーの sha256 は `6d3128e946bc9c95` で始まります。実行は、与えられた開始行を記録し、それを再生します。記録がない場合、何らかの処理を停止する前に、再起動は拒否されます。

実行の開始時に、記録された `OLLAMA_*` と `LLAMA_ARG_*` の完全なセットは、実行中のプロセスの環境と比較されます。この比較は正確に行われます。プロセスの環境を読み取ることができない場合、サーバーの `server config` ログ行が代替として使用され、その比較も正確に行われます。記録されたデフォルトの一部のみを含む記録は、再起動を無効にします。不一致がある場合、この実行では再起動は行われません。その理由は、実行マーカーに `ollama_restart_disabled` として記録されます。何も停止されません。`OLLAMA_HOST` は、`http://` または `https://` スキーマの有無にかかわらず一致します。

サーバーが復旧した後、実行はライブラリの sha256 を `library_path` から読み取ります。フラッシュアテンション、KV キャッシュのタイプ、`load_backend` 行、および完全な `OLLAMA_*` および `LLAMA_ARG_*` セットは、スプawn 後のログに書き込まれたバイトから読み取られます。それより前のバイトは、前のサーバーのものであり、その行は一致しません。ログのサイズを読み取ることができない場合、そのオフセットは不明であり、実行は停止します。ログが存在しない場合、それは空であり、そのオフセットはゼロです。まだ書き込まれていない `load_backend` 行は、最初のモデルのロード後、およびそのサンプルが保持される前にチェックされます。行が存在しないか、異なる場合、実行は停止します。新しいセグメントのサーバー構成行は、実行が測定されたすべての変数をカバーする必要があります。プロセスが設定しなかったデフォルトもログに記録される場合があります。異なるライブラリまたは異なる環境で復旧したサーバーは、実行を停止させます。`nvidia-smi` からのドライバーの CUDA バージョンは、チェックの対象ではありません。再起動では、それを変更することはできません。ログにエコーされないフラッシュアテンションと KV キャッシュのタイプは、一致に失敗します。それらは記録からコピーされず、読み取りとして扱われます。

サーバーが 60 秒以内に正常に動作しないか、カードがベースラインに戻らない場合、実行は停止し、ユーザーが Ollama を開始する必要があると表示されます。1 回の実行で再起動できるのは最大 2 回です。再起動が失敗した場合、その回数は上限にカウントされます。

各再起動は、実行マーカーと `settings.ollama_restarts` に記録されます。具体的には、いつ、どのポート、理由 (`down` または `hung`)、古い PID と新しい PID、正常になるまでの時間、およびバージョンです。実行中にあったステップは、決定的なものではなく、合格とは見なされません。それは、仕様で `retry` が設定されている場合 (デフォルトはなし) にのみ、再度試行されます。保持された再試行は、`settings.retried` を設定します。再起動後の最初の保持されたサンプルは、`settings.cold_after_restart` を設定し、ウォームパーセンタイルから除外されます。再起動を跨いで実行された測定値は、保持されません。

`--dry-run` は、このポリシーを出力し、どちらのポートにも接続しません。
